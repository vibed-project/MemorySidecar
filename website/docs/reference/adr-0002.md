# ADR-0002 — Graph Building Block

> Adds a sixth building block to the sidecar. Reproduced here for
> site-internal navigation; the authoritative copy lives at
> [docs/decisions/adr-0002-graph-building-block.md](https://github.com/m-koerbaecher/memsidecar/blob/main/docs/decisions/adr-0002-graph-building-block.md)
> in the repo.

**Status:** Accepted · **Extends:** [ADR-0001](./adr-0001.md) · **Decision
drivers:** relationship-aware recall as a first-class primitive;
bring-your-own backends; framework-agnostic protocol

## 1. Context

ADR-0001 established five blocks — `kv`, `episodic`, `semantic`, `artifact`,
`lease` — covering caching, history, similarity recall, blobs, and
coordination. None of them models **relationships between entities**.

Agentic workloads increasingly need to ask *connected* questions: "what is
reachable from this entity," "what links these two records," "expand the
neighborhood around what semantic search just returned." The `semantic` block
answers *similarity* ("what is like this?"); it cannot answer *relationship*
("what is connected to this, and how?"). `kv`/`episodic` can encode edges by
convention but offer no indexed multi-hop traversal, so every agent that needs
a graph stands up a graph database directly — reintroducing the per-agent
backend coupling, absent policy enforcement, and namespace sprawl ADR-0001 set
out to remove.

## 2. Decision

Add a sixth building block, **`graph`**: structured **node/edge upsert** and
**bounded traversal** primitives over the same gRPC protocol (plus the
HTTP/JSON mirror), scoped by the existing namespace + capability + policy
model. A `graph.Driver` interface ships with an **in-memory reference driver**
and a conformance suite; at least one production-grade driver follows before
the block is marked ready.

This is additive — it introduces no new cross-cutting subsystems and reuses
the auth, policy, observability, config, and registry machinery from ADR-0001
unchanged.

### Goals

- **Relationship-aware recall as a first-class primitive** — nodes, typed
  edges, and bounded traversal, not relationships smuggled through KV keys or
  flat metadata.
- **Same contracts as the other blocks** — namespace-scoped,
  capability-secured, policy-hooked, OTel-instrumented.
- **Bring-your-own graph backend** — a driver interface selected in YAML like
  every other backend.
- **Composable with `semantic`** — an agent can seed a traversal from the ids
  a semantic search returned, enabling hybrid recall **assembled by the
  agent**, not the sidecar.

### Non-goals

- **Not a graph database** — the block *fronts* graph engines; it does not
  implement storage, indexing, or a query planner.
- **Not a graph query language** — no Cypher/Gremlin/SPARQL as the primary
  surface. A backend-native pass-through is an open question, not a v1
  commitment.
- **Not a reasoning/inference engine** — no ontology reasoning, entity
  resolution, or automated relationship inference. The agent decides what
  nodes and edges to write.
- **Not a context-window compiler** — hybrid retrieval orchestration
  (semantic seed → graph expand → rank → assemble) stays in the agent.

## 3. API surface

```proto
service Graph {
  rpc UpsertNodes(UpsertNodesRequest) returns (UpsertNodesResponse);
  rpc UpsertEdges(UpsertEdgesRequest) returns (UpsertEdgesResponse);
  rpc GetNode(GetNodeRequest) returns (Node);
  rpc Neighbors(NeighborsRequest) returns (NeighborsResponse); // 1-hop, filtered
  rpc Traverse(TraverseRequest) returns (Subgraph);            // bounded multi-hop
  rpc DeleteNode(DeleteNodeRequest) returns (Ack);  // with edge-cascade option
  rpc DeleteEdge(DeleteEdgeRequest) returns (Ack);
}
```

`Neighbors` and `Traverse` are deliberately **structured**: the caller
specifies node/edge type filters, direction, depth, and fan-out/result caps.
There is no free-form query string in v1. This keeps the protocol portable
across backends and keeps traversal cost bounded — depth and fan-out are
**hard-capped server-side** and surface as `ResourceExhausted`. See the
[Graph block reference](../blocks/graph.md).

## 4. Data model

Extends ADR-0001 §6 rather than replacing it:

| Concept | Definition |
|---|---|
| **Node** | `(id, labels, props, created_at)` within a `graph` namespace. The `id` is caller-supplied so it can be shared with a `semantic` record id for hybrid recall. |
| **Edge** | A typed, directed relationship `(id, type, from, to, props, created_at)` between two nodes in the same namespace. |
| **Namespace** | Isolation/grouping boundary, scoped to the `graph` block — same semantics as every other block. |
| **Traversal** | A bounded, structured read (1-hop neighbors or depth-limited expansion), always subject to server-side depth/fan-out caps. |

Edges do not cross namespaces. Cross-namespace or cross-tenant linking is out
of scope.

## 5. Candidate backends

| Driver | Role |
|---|---|
| **in-memory** | Reference + conformance baseline (ships first). |
| Embedded graph engine | Single-binary self-hosted (may introduce cgo / static-binary friction). |
| Standalone graph DB | Production / shared, speaks its native protocol behind the driver. |
| Graph-over-Postgres | Reuses the existing Postgres substrate at the cost of traversal performance. |

Exact products are an implementation choice, not an ADR commitment. The
in-memory driver ships first; at least one production driver follows before
the block is considered ready.

## 6. Status in the walking skeleton

Implemented: `internal/graph/` with the in-memory reference driver **and a
production Postgres driver**, both passing the shared conformance suite;
structured `Neighbors`/`Traverse` with server-side hard caps (depth,
max-nodes, max-edges, per-node fan-out); and the standard auth/policy/config
wiring — including the policy `cap` effect for bounding traversal magnitude.
The block is now backend-pluggable (`memory` | `postgres`).
